Functions

~45 minEverything in ENSC 251 is built from these

A function is a named, reusable block of code. You give it inputs (parameters), it does a job, and it can give back one answer (its return value).

Think of it like

A vending machine. You put something in (money and a button number = arguments), it does its job inside where you can't see, and something comes out (a drink = the return value).

void functions: do something, return nothing

Declaration vs definition

C++ reads top to bottom. If main() calls a function that's written below it, the compiler doesn't know about it yet. Fix: put a declaration (also called a prototype) at the top. It's just the first line, ending with ;.

This is exactly the pattern for classes: member functions are declared inside the class and defined below it with ClassName:: (Chapter 3).

Call-by-value vs call-by-reference

This idea comes back in almost every chapter, so take your time here.

Call-by-value (default)

The function gets a copy. Changing it inside the function does not change the original.

Call-by-reference (&)

The function gets the original variable (really its address). Changes do affect the caller.

When to use which
  • The function needs to change the caller's variable → int&
  • The function needs to send back more than one answer → reference parameters (like found and location in binary search)
  • A big object you only read → const Thing& (fast, and safe). See Chapter 6.
  • Small values you only read → plain value is fine

Local variables and scope

Variables made inside a function exist only while that function runs. Each call gets fresh ones. Two functions can both have a variable called i without any conflict. (This matters a lot for recursion, where each call has its own copy.)

Overloading: same name, different parameters

The compiler picks the version whose parameters match. You'll see this with set() and constructors in Chapters 3 and 4.

Exam trap: going out of bounds

With int a[5], writing a[5] is outside the array. C++ does not stop you. It quietly reads or overwrites some other memory, causing weird bugs or crashes. The classic cause: writing i <= SIZE instead of i < SIZE. This is the “boundary error” from the debugging list.

Arrays have a fixed size that must be known when you declare them. You can't make one grow later. That limitation is the reason dynamic memory and linked lists exist.

Passing arrays to functions

Arrays are not copied

When you pass an array, the function gets the address of the first element, not a copy. So changes inside the function affect the original, a bit like call-by-reference. Use const when the function should only read it. The function also can't know the array's length, so you always pass the size too.

C-strings: text as a char array

Old-style C text is a char array that ends with '\0'. That's why the StringVar class in Chapter 8 allocates max_length + 1 characters. The string type (string s = "Bob";) is the easier modern version, but the course uses C-strings to teach memory.

Chapter 1 · Slide Set 1

The big idea: object-oriented programming

~25 minDeitel 9.1–9.9

There are different styles of writing programs. This course teaches the object-oriented style, where a program is a group of objects that each look after their own data.

Programming paradigms (styles)

A paradigm is a way of thinking about how to write a program. The slides compare three:

Imperative: a list of commands

The program is a sequence of commands: do this, then this, then this. That's how you wrote code in ENSC 151. It's the easiest style to learn because people already think this way.

Think of it like

A to-do list. “1. Boil water. 2. Add pasta. 3. Wait 10 minutes. 4. Drain.” You say exactly how to do it, step by step.

Declarative: describe the result

You say what you want, not how to get it. The computer works out the steps. SQL is an example: SELECT name FROM students WHERE grade > 90 doesn't say how to search.

Think of it like

Ordering at a restaurant. You say “pasta, please”, and you don't explain how to cook it.

Object-oriented: objects that look after themselves

The program is made of objects. Every object has two things:

PartMeaningIn C++ it's calledExample: a bank account
StateWhat it knowsmember variables (data members, fields)balance, interest rate
BehaviourWhat it can domember functions (methods)deposit, withdraw, add interest

Class vs object

A class is the design. An object is one actual thing built from that design. An object is also called an instance of the class.

Think of it like

A class is the blueprint for a house. An object is one real house built from it. You can build 100 houses from one blueprint, and each one has its own paint colour (its own state).

The three pillars of OOP

Memorize these three words. They come up again and again, and they're a classic short-answer question.

1. Encapsulation

Put related data and functions together in one class, and hide the inside details. Every object is responsible for its own data. Nobody outside should reach in and change it directly.

Think of it like

A car. You use the steering wheel and pedals (the public interface). You don't touch the fuel injectors directly (the hidden implementation). The engine can be redesigned and you still drive the same way.

2. Inheritance

Make a new class by extending an existing one. The new class gets the old class's behaviour for free, and you add only what's new. This means you reuse code instead of copying it.

Example: a SavingsAccount is a BankAccount plus deposit and withdraw.

3. Polymorphism

“Poly” means many, “morph” means form. One name can have several meanings depending on the type of object. It gives you a single interface for objects of different types. (You'll see this in more depth later in the course.)

Exam trap

Using C++ does not mean your code is object-oriented. The slides make this point twice: most people who write in object-oriented languages still write imperative-style code. OOP is a way of designing, not just a language feature.

A quick note on how a computer runs

The slides show a simple picture: input → processor (CPU) + memory → output. The review question asks about realistic constraints on a computing system. Good answers: processor speed, memory size (and stack size), power use, cost, and in embedded systems, very limited memory. Keep this in mind when you get to recursion and memory leaks later. Memory is finite.

Why reaching inside an object is bad

With version 1, code outside can do today.month = 13;. Month 13 makes no sense, and nothing stops it. There's a bigger problem too:

  • If you later change how the data is stored (say, from int month to a char code), every piece of code that touched today.month breaks.
  • If everyone goes through a fixed set of functions, you only fix the class. The rest of the program doesn't change.
The OOP ideal

You should never access an object's data directly from outside. Only go through its member functions. Those functions are the object's interface, like an API.

Chapter 4 · Slide Set 2

Constructors: starting objects safely

~45 minDeitel 9.1–9.9, 10.1–10.3

A constructor is a special member function that runs automatically when an object is created. Its job is to give the object a known starting value.

Why we need them

An uninitialized variable holds garbage. int x; could be anything. Objects have the same problem: a fresh BankAccount might have a balance of −8,372,991. Constructors fix this by setting every member the moment the object is born.

The three rules of constructors

1. Same name as the class

The constructor of BankAccount is called BankAccount.

2. No return type

Not even void. No return value, no type written.

3. Should be public

Otherwise nobody outside could create objects of the class.

In BankAccount::BankAccount, the first BankAccount is the class, and the second is the constructor's name.

Creating objects

Exam trap: the empty parentheses

BankAccount account4(); does not create an object. C++ reads it as declaring a function named account4 that takes no arguments and returns a BankAccount. It compiles without an error, so the bug is hard to spot. Later, account4.update(); gives a confusing error.

Fix: BankAccount account4; with no parentheses.

Constructor parameters vs member variables

BankAccount account1(100, 2.3); does not break the “don't touch private data” rule. You're passing values to the constructor's parameters (dollars, rate). Those are different variables from the private members. Only the constructor, which is a member function, copies them in.

The default constructor trap

This is one of the most tested ideas in the chapter:

  1. If you write no constructors at all, the compiler gives you a free default constructor that does nothing (members stay uninitialized).
  2. As soon as you write any constructor, the free one disappears.

Calling a constructor explicitly: anonymous objects

BankAccount(999, 99, 5.5) creates an anonymous object, one with no variable name. Then = copies it into account1. It works, but it's wasteful: a whole new object is built just to copy it. To change values after creation, use a mutator like set(). Constructors are for starting objects, mutators are for changing them.

So why does explicit calling matter? Because of dynamic memory. When you build linked lists, you'll write new Node(5, head), which creates an object on the heap and runs its constructor. Remember this for Chapter 11.

Modern extras (C++11): member initializers and delegation

Member initialization: give a default value right where the member is declared. Useful in critical systems so every field always starts at a known value.

Constructor delegation: one constructor calls another, so you don't repeat code.

Limitation of delegation

If you delegate, the delegation must be the only thing in the initialization section. You can't also write : BankAccount(0,0,0.0), balance(5). Also, two constructors must never delegate to each other in a circle (A calls B, B calls A), or construction never finishes.

Summary
  • Make constructors public. Always include a default constructor.
  • Overload constructors so objects can be created with different amounts of information.
  • Don't use constructors to re-initialize. Use mutators. If you never need to change values after creation, you might not need mutators at all.
Chapter 5 · Slide Set 2

Abstract data types and inheritance

~35 min

An ADT is a type you can use without knowing how it works inside. Inheritance lets a new class reuse everything from an old one.

Data type vs abstract data type

A data type is a set of values plus the operations allowed on them. int is the numbers, plus + - * / and so on.

A type is abstract if programmers using it cannot see or depend on how values are stored or how operations work.

  • int and double are abstract. You don't know exactly how the CPU does *, and you can't use that detail in your program.
  • Your own classes are not automatically abstract. If you make the data public, people can poke at it, and you lose control.

The 3 rules for making a class an ADT

Memorize
  1. Make all member variables private.
  2. Make the operations the user needs public member functions, and fully explain how to use each one in comments.
  3. Make all helper functions private.

Interface vs implementation

Interface (the “what”)

The public member functions + the comments that explain how to use them.

This is all a user needs to know. Once it's set, don't change it.

Implementation (the “how”)

The private member variables + private helper functions + the bodies of all member functions.

You can change this whenever you want.

Because the two are separate, one person can write code that uses the class while another person writes its insides, at the same time. You can make the split even stronger by putting the interface in a header file (.h) and the implementation in a separate .cpp file.

Proof that it works: changing BankAccount's insides

Original: double balance;. New version: store dollars and cents as two ints.

get_balance() still returns the same kind of value, so no code using BankAccount needs to change. You could even delete the private fraction helper and rewrite update() without it. Nobody outside would notice.

Friend functions and const

~35 minDeitel ch. 9 to 9.18 · Savitch 11.1–11.2

A friend function is a normal function that's allowed to see a class's private data. const is a promise that something won't be changed.

The problem: comparing two dates

We want a function equal(date1, date2) that returns true if two DayOfYear objects are the same day. Where should it go?

Option A: a member function. Then you'd call date1.equal(date2). That works, but it treats the two dates unequally. One is “the caller” and one is “the parameter”, even though comparing is symmetric.

Option B: a normal (non-member) function using accessors.

This works but is inefficient: every comparison calls four accessor functions, and each call has overhead. We'd like to write date1.month == date2.month directly, but that's illegal because month is private.

The solution: friend

Friend facts
  • A friend is not a member function. It's an ordinary function with special access.
  • It's listed inside the class definition with the keyword friend, usually in the public section.
  • It's defined like a normal function: no ClassName::, and you don't repeat the word friend.
  • It's called like a normal function: equal(a, b), not a.equal(b).
  • A class can have many friends.

Exam trap: do friends break encapsulation?

Partly. A friend reaches into private data, so if you change the class's private members, you may have to rewrite the friend too. That's the cost. Don't make everything a friend. Keep accessors and mutators as the clean interface, and use friends only where they make code simpler and faster.

Call-by-value vs call-by-reference

Look at equal(DayOfYear date1, DayOfYear date2). These are call-by-value parameters: each call copies the whole object. For big objects, that's slow.

Call-by-reference (DayOfYear& date1) passes the object's address instead. Nothing is copied, so it's faster. The catch: the function can now change the original object.

Solution: use const together with reference. You get the speed of reference, and the compiler stops anyone from changing it.

Put const in both the declaration and the definition.

Operator overloading

~40 minDeitel 11.1–11.4

Operators like + and << are really just functions with a special way of calling them. So you can write your own versions for your own classes.

The idea

Instead of total = add(cost, tax); we want total = cost + tax;. In C++, a + b is really a call to a function named operator + with arguments a and b. You overload it like any function, using the keyword operator.

The 7 rules of operator overloading

Memorize: these are classic exam questions
  1. At least one argument must be a class type. You can't redefine + for two ints.
  2. An overloaded operator can be a friend, a member, or an ordinary non-friend function.
  3. You cannot create new operators (no ** or <>).
  4. You cannot change the number of arguments. * stays binary and ++ stays unary.
  5. You cannot change precedence. a*b-c always means (a*b)-c.
  6. You cannot overload: . (dot), :: (scope resolution), .* and ?:.
  7. = (assignment), [] and -> are overloaded differently (they must be members). See Chapter 9 for =.

Automatic type conversion

Just as C++ converts int to double automatically, it can convert to your class if you have the right constructor.

How? How does base_amount + 25 compile?
  1. The compiler looks for operator +(Money, int). There isn't one.
  2. It looks for a constructor that takes one int (or long) and builds a Money. There is one: Money(long dollars).
  3. It converts 25 into Money(25), which is $25.00, and calls operator +(Money, Money).
Predict Does full_amount = base_amount + 25.67; work?

It compiles, but it's wrong. There's no constructor that takes a double, so C++ quietly converts 25.67 to the long 25 (dropping the .67) and uses Money(long). You lose 67 cents with no error at all. Fix: add a constructor Money(double amount); that converts dollars-with-decimals into cents. (Some notes say this line won't compile. g++ compiles it.)

++ and --

If you overload ++ the normal way, you get the prefix version (++x). The postfix version (x++) is declared differently, with a dummy int parameter: Money operator ++(int);. The slides say this is optional reading.

Overloading << and >>

We want cout << amount; instead of amount.output(cout);.

Why? Why amount.all_cents instead of just all_cents?

Because operator << is a friend, not a member. It has no “calling object”, so plain all_cents means nothing. It has to say whose all_cents.

Dynamic memory: new and delete

new creates a variable at run time in a memory area called the free store, and returns a pointer to it.

delete destroys it and gives the memory back so it can be reused.

Three dynamic-memory traps
  1. Memory leak: if you new something and never delete it, that memory is lost until the program ends. Even if the pointer was a local variable that disappeared, the memory it pointed to does not. Do it enough times and the program runs out of memory and crashes.
  2. Forgetting []: delete value; on an array compiles, but likely won't free the whole array. [] tells delete to find the array's length and free all of it.
  3. Never mix C++'s new/delete with C's malloc/free. They manage different memory pools (the free store vs the heap), so new + free or malloc + delete can corrupt memory.

A C-string (a char array used as text) ends with the null character '\0'. That's how functions like strlen, strcpy and cout know where the text stops. So an array for up to max_length characters needs max_length + 1 slots.

The copy constructor and operator=

~45 minHard, but very testable

When an object holds a pointer, copying it the default way copies only the address. Then two objects share one piece of memory, and things blow up. The copy constructor and a custom = fix this.

Shallow copy vs deep copy

Shallow copy (the default)

Copies each member as-is. For a pointer, that copies the address. Both objects now point at the same array.

Deep copy (what you write)

Allocates a new array and copies the contents into it. Each object has its own memory.

Think of it like

Shallow copy: giving a friend a copy of your house key. You now share one house. If they knock it down, your house is gone too. Deep copy: building them their own identical house.

The copy constructor

A copy constructor is a constructor with one parameter of the same class type, passed by reference, normally const.

Think Why must the parameter be a reference?

If it were call-by-value, then passing the object would need a copy, which would call the copy constructor, which needs a copy, which calls the copy constructor... forever. Passing by reference avoids making a copy in the first place. const promises we won't change the original.

When is the copy constructor called automatically?

Three times
  1. Initializing a new object from an existing one: StringVar temp(line); or StringVar temp = line;
  2. Passing by value to a function: void show_string(StringVar the_string)
  3. Returning by value from a function: return temp;

Not with assignment on an existing object: a = b; calls operator= instead.

Testing, debugging and design for testability

~25 minMostly vocabulary: easy marks

Good programmers plan how to test before they write code, and debug methodically instead of guessing.

Preconditions and postconditions

Comments are part of your interface. A good function comment says:

  • Precondition: what must be true before the call (what you expect as input).
  • Postcondition: what will be true after the call (what it produces).

Don't describe the private member variables in these comments. The user shouldn't need to know them. A user should understand how to call the function without ever seeing its body.

Writing the interface first lets team members work in parallel, and helps you list every test case you'll need.

Unit testing (Agile)

  • Write a set of test functions for each module, before writing the code.
  • Write only enough code to pass the tests, and no more. The tests may be clunky, but the real code ends up clean.
  • Test each function alone first, then inside the full program (ideally after every other function was already tested).
Every test set needs three kinds of cases
  1. Normal cases: typical inputs.
  2. Boundary / corner cases: the edges. Empty list, one item, first or last item, 0, the maximum size.
  3. Illegal cases: bad inputs. Negative money, month 13.

Drivers and stubs

Driver (testbed)

A temporary program whose only job is to call the function you're testing with different inputs and show the results.

Stub

A fake, simplified version of a function that isn't written yet, so you can test the functions that call it.

In practice, about 99% of serious testing uses file I/O: read many test inputs from a file, write outputs to a file, and compare them offline. You can run a big batch, and the output can even flag which tests failed. (This is why output(ostream&) takes a stream.)

Top-down vs bottom-up

ApproachHowTool
Top-downWrite the main program first with stubs for every function. Replace stubs one at a time, testing after each.Stubs
Bottom-upWrite and test the small low-level functions first, then build up to the main program.Drivers

Top-down's idea: if every function was tested before the next was added, a new bug is probably in the newest function. (In reality, not always.)

How to debug, methodically

  1. Check common errors first: uninitialized variables, unwanted automatic type conversion, = instead of ==, off-by-one or boundary errors.
  2. Localize the error: start from a test case you know fails, and use test cases or cout to find where things first go wrong. (Sometimes cout isn't available, for example on embedded systems, so know other ways too.)
  3. Keep an open mind: don't assume you know where the bug is.
  4. Don't randomly change code hoping it fixes things. It almost never works, and you can't localize the bug afterward.
  5. Keep a log of which tests pass and fail, so you don't repeat the same tests.
  6. Assume nothing works. Go line by line.
  7. Rubber duck debugging: explain your code line by line to a rubber duck, or a person. Explaining often reveals the bug.
  8. Use a debugger and watch the program's behaviour.
  9. Use a memory leak checker.

Design for testability: #ifdef DEBUG and assert

These are preprocessor macros: instructions processed before compiling.

Splitting a program into files, and namespaces

~40 minLinker errors make sense after this

Real programs live in many files: a header (.h) that says what a class can do, an implementation (.cpp) that does it, and an application file that uses it. Namespaces stop names from different files clashing.

Why split a program into files

Until now everything went in one .cpp file. Real programs are spread over many files. Each .cpp file is compiled separately, then they're all linked together into one program.

  • Readability: each class lives in its own files.
  • Reuse: write a class once and use it in many programs, just like <iostream>.
  • Less recompiling: change one file and only that file is recompiled. Everything else is just relinked.
  • Reliability: reused code has already been tested and debugged.
Think of it like

The predefined libraries you already use. You write #include <iostream> and use cout without ever seeing its code. Your own classes can work the same way.

The header only declares the functions: it promises they exist. That's enough for the compiler to check every call. The bodies are in dtime.cpp. If that file isn't compiled and linked in, the linker can't find them and stops with undefined reference to `DigitalTime::advance(int)'.

Include guards: #ifndef

With several files, the same header easily gets included twice: main.cpp includes dtime.h, and also alarm.h, which includes dtime.h as well. The class would then be defined twice, and C++ doesn't allow that even when both copies are identical:

Namespaces

On a team of 100 programmers, two people will eventually pick the same name. A namespace is a named collection of definitions (classes, functions, variables), so the same name can mean different things in different namespaces.

  • std holds every name from the standard library: cout, string and so on.
  • Anything you don't put in a namespace goes in the global namespace. (You could write your own cout there, but that's a bad idea.)

A using namespace directive at the top of a file applies to the whole file. Inside braces it applies only to that block, from the line where it appears to the closing brace. A namespace can also be opened in several places, even in different files: dtime.h and dtime.cpp can both say namespace dtimesavitch { … }, and it's all one namespace.

A stack gives back items in reverse order (last in, first out). A queue gives them back in the same order (first in, first out).

Stack = LIFO

A stack of books, or a Pez dispenser. You add to the top and take from the top. Put in A, B, C and you get back C, B, A.

Queue = FIFO

A line at a cashier. People are served in the order they arrived. Put in A, B, C and you get back A, B, C.

Stacks

Two operations: push (add to the top) and pop (remove from the top). In linked-list terms, all inserts and removes happen at the head. An empty stack is an empty list: top == NULL.

Stacks are everywhere in computing: function calls pass data on the stack, and they're the key to how recursion works (Chapter 13).

Practice Write the Stack copy constructor (deep copy)

Why it's needed: the default copy would copy only top, so two stacks would share the same nodes. When one is destroyed, the other points at freed memory.

Queues

Two operations: add (at the back) and remove (from the front). A queue needs two pointers: front (head) and back (tail).

Why? Why does a queue need a back (tail) pointer?

Without it, every add would have to walk the entire list to find the end. That's slow for long queues. Storing one extra address avoids that, which is a big runtime saving for very little memory.

Exam trap

When remove() takes the last item, you must set back = NULL as well. Otherwise back points at deleted memory and empty() returns false for an empty queue.

Big Three for data structures

Stacks, queues and linked-list classes all use new, so they need all three: a copy constructor (deep copy the nodes), a destructor (delete every node) and an overloaded = (delete the old nodes, deep copy the new ones). If Node is a class instead of a struct, the logic is the same. You just use its accessors and constructors instead of ->data.

Recursion

A recursive function solves a problem by calling itself on a smaller version of the same problem, until the problem is small enough to answer directly.

Think of it like

Russian nesting dolls. To find the smallest doll: open the doll. If there's nothing inside, you found it (base case). Otherwise, do the same thing with the doll inside (recursive case). Each doll is smaller, so you're guaranteed to finish.

The two parts every recursive function needs

Base case (stopping case)

A case solved directly, with no recursive call.

Recursive case

Solves the task by calling itself on a smaller input that moves toward the base case.

Usually an if-else chooses between them.

Example 1: write_vertical

Goal: print the digits of a number one per line. write_vertical(123) prints 1, 2, 3 on separate lines.

Break it down:

  • Base case: if n has one digit (n < 10), just print it.
  • Recursive case: print all digits except the last (that's n / 10, a smaller problem!), then print the last digit (n % 10).

Integer math makes this easy: 123 / 10 = 12 (drops the last digit) and 123 % 10 = 3 (gets the last digit).

Why? Why not “print the first digit, then the rest”?

That's a valid way to break it down too, but much harder to code. Getting the last digit is just n % 10, and removing it is just n / 10. Getting the first digit means first figuring out how many digits there are. Choose the decomposition that's easiest to compute.

Step through it: the call stack

This is the most important picture for recursion. Each call gets its own stack frame (activation frame) holding its own copy of n. When a function makes a recursive call, it pauses right there and waits. When the inner call finishes, the paused call resumes exactly where it stopped.

Recursion is not magic. To the computer, a recursive call is just another function call that happens to run the same code with a different argument. Each call has its own scope, so if a caller needs a result, the callee must return it.

Infinite recursion and stack overflow

This compiles, but never stops. Every call pushes another frame onto the stack. The stack is finite, so eventually you get a stack overflow and the program crashes.

  • On a normal computer the stack is large, so overflows are hard to cause by accident. On embedded systems they're a real concern.
  • Deeply nested interrupts can also overflow the stack.
  • If you worry about large inputs, make that a test case. Some systems let you increase the stack size with a linker option.

Recursion vs iteration

Anything recursive can be written with loops instead (an iterative version). Recursion is never strictly necessary.

RecursiveIterative
CodeOften shorter and more elegantOften longer
SpeedUsually slower: many function callsUsually faster: one call
MemoryUses more: a stack frame per callUses less

So recursion makes the programmer's job easier, but costs runtime and memory. For a quick tool on a desktop, recursion is fine. For an embedded controller with tiny memory, prefer iteration.

The 3 criteria for a correct recursive function

Memorize: proving a recursive function is correct
  1. No infinite recursion. Every recursive call moves toward a base case. (power: n drops by 1 each call, so it reaches 0.)
  2. Each base case returns the correct value. (power: x0 = 1. Correct.)
  3. For the recursive cases: if all the recursive calls return correct values, then the final value is correct. (power: if power(x, n-1) is right, then times x is right.)

For void functions, read “performs the correct action” instead of “returns the correct value”.

Criterion 3 should remind you of proof by induction from math: prove the base case, then prove “if it works for n−1, it works for n”.

Binary search

~30 minThe big recursion example

Binary search finds a value in a sorted array by checking the middle, then throwing away the half where the value can't be.

Think of it like

Guessing a number between 1 and 100 when someone says “higher” or “lower”. You guess 50, then 75, then 62... Each guess cuts the possibilities in half.

The idea

If the key is in a sorted list, it's either at the middle, in the first half, or in the second half. One comparison either finds it or cuts the search space in half. Then search the remaining half the same way. That's recursion.

To describe “the remaining half”, the function needs two extra parameters: first and last, the window still being searched. (This is the “solve a more general problem” idea.)

The code

found and location are call-by-reference, so the answer travels back to the original caller. The first call is search(a, 0, final_index, key, found, location);

Checking the 3 criteria

  1. No infinite recursion: each call searches a smaller window (at least one element shorter), so eventually it finds the key or first > last.
  2. Base cases are correct: if first > last there are no elements left, so “not found” is right. If key == a[mid], “found at mid” is right.
  3. Recursive cases are correct: the array is sorted, so if key < a[mid] it can only be in a[first..mid-1]. If key > a[mid], only in a[mid+1..last]. If those calls work, the whole thing works.

Bonus: since it takes first and last, you can use it to search any contiguous part of an array, not just the whole thing.

Common problems
  • C++ only prints characters. The terminal decides whether to treat them as colour commands. Exact shades depend on the terminal.
